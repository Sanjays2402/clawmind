## Theme

Knock out four explicitly-queued items + complete the --above/--below
symmetry on `feedback prune` that the queued list had explicitly
carved out. The common thread is **cron-friendly time-and-budget
shaping**: every feature is a small dial an operator scripting cron
ticks reaches for to express "less work, focused on the right
window":

- `feedback prune --above` = "clear the over-cap entries after a
  cap recalibration"
- `pins/mutes list --since` = "what got pinned/muted in the last 24h"
- `doctor --json --quiet` = "is the index ok? how many errors?" in
  5 fields for tight dashboards
- `reindex --since` = "rebuild from scratch but only walk recently-
  modified files"
- `digest run --since` = "re-run only digests that haven't run
  in the last hour"

## Notable design choices

- **`reindex --since` validates BEFORE any mutation.** The live path
  runs the manifest+BM25 wipe FIRST then calls ingest, so a typo'd
  cutoff landing mid-flight would leave the index in a partial
  state the operator could only recover from with a full reindex
  (defeating the whole purpose of the flag). Hard-fail up front.
- **`feedback prune --above + --below` is OR, not AND.** When both
  flags are set the predicate is "trim both tails": clear everything
  below the floor OR above the ceiling. The natural use is
  "clear everything outside the neutral band" — an AND semantic
  ("must be both above the ceiling AND below the floor") is
  mathematically empty so OR is the only useful interpretation.
- **`digest run --since` uses strict less-than (<), not <=.** A
  digest with `lastRunTs === cutoff` is SKIPPED — it ran AT the
  cutoff, satisfying the operator's "leave alone if it ran within
  the last hour" intent. Re-running would be more eager than asked.
  Counterintuitively, lastRunTs === null (never-run) is ALWAYS
  INCLUDED because a never-run digest is the most extreme case of
  "needs running" — a filter that hid never-runs would be unsafe
  for any saved search the operator just added.
- **`doctor --json --quiet` keeps the FULL findings tally even when
  --severity hides some rows from view.** The slim shape exists for
  an "are we ok?" question that needs the unconditional count, not
  the filtered display count. `ok` mirrors `r.ok` (the full report's
  flag) so hiding rows via --severity never accidentally hides an
  unhealthy report from the slim shape. Exit code still reflects
  r.ok so wrapper scripts reading only the exit code still detect.
- **`pins/mutes list --since` is a single feature touching two
  files.** The symmetry is what makes the cron use real (`pins list
  --since X --paths` and `mutes list --since X --paths` must behave
  identically); splitting them would have created an asymmetric
  CLI surface that a cron operator scripting daily snapshots would
  have to special-case around.
