## Family-wide --slim cron-dashboard contract

After this tick, NINE cli commands carry the `--slim` contract:

| Command                       | Tick | Shape                                              |
|-------------------------------|------|----------------------------------------------------|
| `feedback prune --json --slim`| 11   | full-shape minus `paths` array                     |

| `stats --json --slim`         | 5    | `{stale, total}` namespace name list               |
| `feedback list --json --slim` | 12   | `{count, neutralCount, upDominantCount, downDominantCount}` |
| `search --json --slim`        | 12   | per hit `{rank, path, score, namespace}`           |
| `related --json --slim`       | 12   | per item `{path, score, namespace}` + sourceChunkCount |
| `aliases list --json --slim`  | 12   | `{count, names}`                                   |
| `digest list --json --slim`   | 12   | `{count, overdueCount, neverRunCount}`             |

The five contract properties uniform across all nine:

1. Single-line `JSON.stringify` (no indent) so NDJSON snapshot streams
   diff cleanly between ticks.
2. Drops the per-entry heavy fields the dashboard does not need.
3. Emits a small set of integer counts + (optionally) a single array
   of identifiers.
4. Composes with every filter/sort the command already supports — slim
   describes the SURVIVORS.
5. Silently ignored without `--json` (text mode for humans unchanged).

## Notable per-feature design choices

### 1. feedback list --json --slim (5d21b7a)

Four buckets carve the boost distribution at neutral with **strict
comparisons** at `1.0`:
- `upDominantCount` (boost > 1.0)
- `downDominantCount` (boost < 1.0)
- `neutralCount` (boost === 1.0)
- `count` (always = sum of the three)

The strict split mirrors the `feedback list --above 1.0` / `--below 1.0`
strict semantics the operator already knows. Sum-equals-total invariant
pinned.

### 2. search --json --slim (713649a)

The CRITICAL perf property: the slim path does NOT call `snippetFor()`.
A dashboard polling once a minute over a 50-result top-k must not pay
50 snippet renders per poll. Pinned by:

```ts
expect(snippetForMock).not.toHaveBeenCalled();   // slim path
expect(snippetForMock).toHaveBeenCalled();       // default --json path
```

— so the perf claim is auditable BOTH ways. Without the baseline
assertion, a future regression that silently stopped calling snippetFor
in the default path would make the slim perf claim vacuous.

Precedence pinned: `--paths-only > --slim > --no-snippet > full --json`.

### 3. related --json --slim (7bc727f)

Critical contract: `sourceChunkCount` (the source's own chunk count)
is PRESERVED verbatim even when `--threshold` drops every neighbour to
zero. The dashboard wants to know "foo.md has 47 chunks but ZERO
neighbours pass my threshold" as TWO separate numbers, not as a
collapsed single "0".

### 4. aliases list --json --slim (71cb531)

`names` array carries WHICHEVER ORDER the prior filter+sort pipeline
produced. Switching `--slim` on/off must NOT flip the ordering — slim
mirrors the full shape's item order. Pinned by a test that
`--sort name --reverse` produces desc-alphabetical names.

Note on the `--json > --paths` precedence: the existing aliases code
already has `if (opts.json) { ... }` BEFORE the
`if (opts.paths || opts.pathsOnly) { ... }` branch. `--slim` lives
INSIDE the `--json` branch so the existing precedence is unchanged —
documented explicitly in the `--slim` help text so a future reader
sees the precedent.

### 5. digest list --json --slim (abec248)

Three buckets `{count, overdueCount, neverRunCount}` — `neverRunCount`
exists as its own bucket because "added a saved search but never ran
it" is operationally DISTINCT from "ran it once but it has gone stale"
— the two have different remedies. Sum-equals-total invariant pinned
across three fixtures (all-never-run, all-timestamped, empty).

Composes with `--since` for the canonical overdue audit. Pairs with
`digest run --since "..." --json --slim` (the sibling slim shape that
ran 12 ticks ago on tick 7) as the read+write side of the same
overdue question.
