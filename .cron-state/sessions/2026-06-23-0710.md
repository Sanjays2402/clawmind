## Process notes

1. **Stale .d.ts/.js sidecars caused initial test failure.**
   `apps/cli/src/commands/reindex.d.ts` (etc.) were shadowing the
   source `.ts` files for vitest's module resolution. The first
   `pnpm test -- reindex` run after wiring up `--slim` reported
   "unknown option --slim" because the sidecars predated the
   change. Fix: `rm -f apps/cli/src/**/*.{js,d.ts,js.map,d.ts.map}`.
   These are gitignored (commit d951f11 from 2026-06-21) so they
   don't travel between checkouts — but they accumulate locally
   between ticks if the cli build was ever run. A future tick
   could add a `pretest` clean step to apps/cli/package.json.

2. **Stale's --json precedence over --paths.** The first --slim
   test against stale assumed the family-wide pipeline-beats-
   dashboard precedence (where --paths-only short-circuits before
   --json + --slim). But stale's source order reverses this:
   --json is checked BEFORE --paths/--paths-only/--tsv in
   stale.ts. The test was rewritten to match the actual contract
   and the --slim help text was amended to document the
   stale-specific exception. Behaviour unchanged; only the test
   assertion needed fixing.

3. **doctor --quiet vs --slim semantics.** Considered making
   --slim a pure alias for --quiet, but that would have left the
   queued `--severity` / `--slim` composition question
   unanswered. Resolution: --slim narrows tallies under --severity
   (new canonical semantic); --quiet preserves the legacy
   unconditional-full-counts behaviour (back-compat). When both
   flags are passed, --slim wins. The `ok` flag is always driven
   by `r.ok` from the API regardless of which path is taken, so
   neither flag can promote an unhealthy report to ok=true via
   --severity narrowing.

4. **stats --top under --slim default detection.** The commander
   default for --top is the literal `'4'`. To distinguish "user
   passed --top explicitly" from "default was supplied by
   commander", the slim branch tests `opts.top !== '4'`. This
   means a user passing `--top 4` explicitly still gets the cap
   (string comparison succeeds), but the unflagged invocation
   leaves the slim list unbounded. The detection is fragile in
   principle (commander could change the default literal) but
   it's the only signal available without restructuring commander
   option parsing. Documented in the action code comments.
